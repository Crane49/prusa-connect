Generated by 'make generate-device-issues' from the descriptor table this build links. Do not edit: change the table in Go and regenerate.

Every device record carries an `issues` array. Each entry is a `reason` from the closed set below and the `severity` that reason is declared with, and that is all it carries. The sentence a person reads is here, so a client branches on the token and a translator translates this page rather than the wire.

The array is ordered, worst first, so the first entry is what somebody should read first. An empty array is a device with nothing wrong.

An issue is what this server has found, not what the machine said. The machine's own words travel in `detail` when a reason has one, and they are shown to a person rather than branched on: a firmware may spell one this build has never seen.

## Vocabulary version

This build carries `device-issues` version `1.0.0`, in format `1.0`. The content version moves when a reason is added, retired or redefined; the format version moves when the shape of an entry changes.

## Severities

A severity belongs to the reason and never to one device, so every record carrying a reason carries the same severity. They are listed least to most urgent, and a device showing one badge shows the highest its issues carry.

1. `info`
1. `warning`
1. `error`

## The set

Each reason below is its own section, anchored by the token, so a client's comment can link to the reason it handles.

### `awaiting_operator` {#awaiting-operator}

The device raised a dialog and is waiting for a person.

- **severity** `error`

The device put a question on its own screen and stopped. Nothing this server sends moves it on except an answer to that dialog, so a job does not continue until somebody answers it. The host reads it from the reserved dialog subtree of the state tree: /dialog/id raises this issue, and /dialog/title, /dialog/text and /dialog/code are what the machine displayed, in the machine's own words.

**What to do:** Read the dialog title and text on the device record, then answer it at the machine or with the dialog action verb.

### `departed` {#departed}

The device's session has ended, so nothing can be sent to it.

- **severity** `warning`

The connector released the device. What the record carries is the last reading this server took, and every operation that has to reach the machine is refused until it dials in again. A printer switched off overnight reads this way, so it is not a fault on its own. It is the only issue a departed device carries: the rest of the record describes a machine nothing is talking to, and reporting a stale dialog as live work would send somebody to a printer that is off.

**What to do:** Read the departed member for why the session ended and when. Check that the machine is powered and on the network.

### `disconnected` {#disconnected}

The session is held and no connection to the device is up.

- **severity** `warning`

The connector still holds the session, so a command queues instead of failing, and the machine is not answering now. It is what a device that lost power or fell off the network looks like before its session ends.

**What to do:** Check power and the network. A command sent now waits until the device answers again.

### `frames_refused` {#frames-refused}

The device is sending frames its driver has no reading of.

- **severity** `warning`

The driver dropped frames it could not read, over the window the link member reports. Anything above zero on a connected device is firmware speaking something this build does not know, and it stays connected and silent while it does. A driver that counts nothing never raises this: no measurement is not a clean link.

**What to do:** Read the refused frame rate under link, then report the model and the firmware version so the dialect can be covered.

### `telemetry_dropped` {#telemetry-dropped}

This server is not reading the device's telemetry fast enough.

- **severity** `warning`

The session discarded state patches because this server was behind, so the state tree is older than the machine. It is load on this server rather than a fault at the device. A dialog is never discarded: it holds a slot the queue cannot evict, because a dropped dialog is repeated by nothing.

**What to do:** Read the dropped telemetry rate under link. Reduce what this server is doing, or give it more of the machine it runs on.

### `no_capability_profile` {#no-capability-profile}

No capability profile covered this model and firmware.

- **severity** `info`

The capability set was resolved from the driver's baseline alone, so the device works and offers fewer verbs than a covered device of the same model does. A model this build has never seen and a firmware newer than the profiles it ships both read this way.

**What to do:** Compare the capabilities member against a covered device of the same model, and report the model and firmware so a profile can be added.

## The rollup on a fleet listing

`GET /api/v1/devices` carries an `issues` member beside the page, holding `affected` and a `counts` key for every reason below. It is over every printer the caller may see, whatever page was asked for and whether or not `with_issues` narrowed it, so one request loads a page and the badge that goes beside it.

`with_issues=true` narrows the page to the printers carrying at least one issue. It costs no extra query: an issue is read from what the server already holds for a device it has been dialled by.

## Reading the set from a running server

`GET /api/v1/vocabularies/device-issues` answers with what **this build** raises, from the same table this page is generated from. A client reads it before it holds a credential, which is why it takes none.
