The access check answers one question: may the caller, who is always you,
perform this action on this object? A page uses it to grey a button before
the person clicks it, so a refusal is something the page knew about and not
something the server had to say.

The answer comes from the same rows the server enforces on. It lists every
action you hold on the object, and `allowed` says whether the one you asked
about is among them. Nothing is written and no permission is needed, because
anyone may ask what they themselves may do. The answer also carries
`authorization_epoch`, a counter that moves whenever a grant is written or
withdrawn. A cached answer with an older epoch is worth asking again.

## Which operation to call {#which-operation}

| you want to | call |
|---|---|
| decide whether to show a control on one object, or which controls to show | [`check-access`](#check-access) |

A printer row in `list-devices` already carries its `actions`, so a fleet
page needs no check per printer.

The answer is a hint. The server decides again when the action arrives, and
a grant written in between changes the outcome. An object this server has
never seen answers the same way as one you cannot reach, so the check cannot
tell you which printers exist.

## Operations {#operations}

### `check-access` {#check-access}

`POST /api/v1/access/check`. What the caller may do to one object.

Answers whether the caller may perform one action on one object, and lists every action they may perform on it. The subject is always the caller: this operation cannot ask about anybody else, and it needs no permission of its own, because a caller may always ask what they themselves may do.

Use it to render an interface: grey a control the caller cannot use, instead of attempting the action to find out. The fleet listing already carries the same set on every printer row, so a client drawing a list of printers does not need this operation at all.

The answer is a hint and never the decision. The server checks the permission again when the action is attempted, and a grant written in between changes what it says. Compare `authorization_epoch` against the value on a cached answer to see whether one has been.

An object this server does not have answers exactly as an object the caller reaches nothing on: `allowed` false and an empty `actions`. That is deliberate, and it is why this operation cannot be used to find out which printers exist.

A body naming a `subject` is refused. Asking what another principal may do is a separate operation with a permission of its own, and this server has none.

- credential: bearer token. The client method is `checkAccess`
- request body: `application/json` (`AccessCheckBody`), required
- response `200`: OK, `application/json` (`AccessDecision`)
- errors: `400`, `401`, `422`, `500`, each a [problem document](../../error-codes.md)

#### Sample {#sample-check-access}

```sh
curl -X POST "http://127.0.0.1:8080/api/v1/access/check" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "action": "operate",
    "object_id": "9f2a4c18-6d3b-4e07-b5a1-8c0f2d7e4b93",
    "object_type": "device"
  }'
```

```ts
await client.checkAccess({
  body: {
    action: "operate",
    object_id: "9f2a4c18-6d3b-4e07-b5a1-8c0f2d7e4b93",
    object_type: "device",
  },
});
```

The server answers `200`:

```json
{
  "actions": [
    "observe",
    "operate"
  ],
  "allowed": true,
  "authorization_epoch": 7
}
```
