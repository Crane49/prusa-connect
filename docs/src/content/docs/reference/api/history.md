History is what this server remembers: the events that happened and the
measurements printers reported, kept in a store and searchable by printer,
by type and by time. The event stream is the present. This is the past.

Nothing is kept unless a history provider is configured, an instance of the
`history` resource kind under [resources](./resources.md). The provider
reads the event stream and writes what it sees, so a record here is a row
the provider caught. A deployment with no provider answers 501 on every path
here. What a caller may read is narrowed by the same graph the stream is
narrowed by, so the past of a printer you cannot see now is not readable
either. Who authorized a command is audit, and those members appear only
for a caller holding `view_audit` on the device.

## Which operation to call {#which-operation}

| you want to | call |
|---|---|
| draw a temperature chart of a past print | [`list-device-history-samples`](#list-device-history-samples), with `metrics` |
| read what happened to one printer | [`list-device-history-facts`](#list-device-history-facts) |
| search events or measurements across the fleet | [`list-history-facts`](#list-history-facts), [`list-history-samples`](#list-history-samples) |
| see every command sent to a printer, and which are still open | [`list-device-commands`](#list-device-commands) |
| read one command by the id the send answered with | [`get-command`](#get-command) |

Every listing pages. Send the `cursor` a page returned back unchanged, and
read nothing out of it, because its form belongs to the provider. A window
the server knows it did not see whole is marked `incomplete` and never
answered as a quiet gap.

## Operations {#operations}

### `get-command` {#get-command}

`GET /api/v1/commands/{command_id}`. Read one command.

Reads the folded command record, which is what a history provider made of the three durable frames every invocation publishes: the instruction, the audit record of who authorized it, and the outcome. A deployment that configures no provider keeps no record and answers 501.

One invocation by the id this server minted for it. An id belonging to a device the caller may not read is answered exactly as an id nothing was ever stored under, so this path discloses no command the caller could not have listed.

Who authorized a command is audit, and the three audit members are absent for a caller who does not hold view_audit on the device. What the command was and how it ended is not audit and is answered to anybody who may read the device. An invocation that was refused before it reached the machine is a record like any other: the id is minted before the authorization check, so a caller who was told no can read back what they asked for.

| parameter | in | type | required | description |
|---|---|---|---|---|
| `command_id` | path | `string` | yes | The invocation's id, as the server answered it when the command was sent. |

- credential: bearer token. The client method is `getCommand`
- request body: none
- response `200`: OK, `application/json` (`HistoryCommand`)
- errors: `401`, `404`, `422`, `500`, `501`, each a [problem document](../../error-codes.md)
