The developer operations are for somebody debugging this server or a printer
at a bench, and not for running a fleet. They show what this build carries
and what this process has done since it started.

Nothing here is stored. The command log is bounded and lives in memory, so a
restart empties it. It records only what this binary sent: nothing a printer
did on its own, and nothing that came through another server. The connector
inventory is read from the binary itself. The developer view at `/dev` is
one HTML page that reads the same operations any other client reads, with
the caller's own credentials. So it shows exactly what those credentials
reach. Every operation takes a bearer token, and the command log is answered
only for a device the caller may read.

## Which operation to call {#which-operation}

| you want to | call |
|---|---|
| see which printer dialects this build carries, and which failed to build | [`get-developer-connectors`](#get-developer-connectors) |
| see what this process sent to one printer and what came back | [`get-developer-device-commands`](#get-developer-device-commands) |
| open the debugging page in a browser | [`get-developer-view`](#get-developer-view) |

For a record that survives a restart, read the [history](./history.md)
page. Its [`list-device-commands`](./history.md#list-device-commands) reads
the same commands from the store a history provider keeps.

## Operations {#operations}

### `get-developer-connectors` {#get-developer-connectors}

`GET /api/v1/dev/connectors`. The connectors this build carries.

Every printer dialect compiled into this binary, whether its routes are being served, and how many capabilities its baseline declares, joined to every path this origin answers that the document does not publish. A dialect that could not be built is reported as failed rather than left out, because a missing row reads as a build that does not carry the dialect at all.

It takes develop_device on the driver resource kind, which an org administrator holds on day one. The surface says what this binary is made of and what it sent to a machine, so it is not conferred by an identity alone and it is not view_resource: reading that a connector is declared is part of seeing the configuration, and this is the bench.

- credential: bearer token. The client method is `getDeveloperConnectors`
- request body: none
- response `200`: OK, `application/json` (`Inventory`)
- errors: `401`, `403`, `500`, each a [problem document](../../error-codes.md)

#### Sample {#sample-get-developer-connectors}

```sh
curl "http://127.0.0.1:8080/api/v1/dev/connectors" \
  -H "Authorization: Bearer $TOKEN"
```

```ts
await client.getDeveloperConnectors();
```

### `get-developer-device-commands` {#get-developer-device-commands}

`GET /api/v1/dev/devices/{device_id}/commands`. The commands this process carried to a device.

What was sent, what came back, and how long it took, for the commands still in this process's bounded log. It records nothing a printer did on its own and nothing that arrived through another server: it is what this binary sent while it has been running.

It takes develop_device on the driver resource kind, which an org administrator holds on day one. The surface says what this binary is made of and what it sent to a machine, so it is not conferred by an identity alone and it is not view_resource: reading that a connector is declared is part of seeing the configuration, and this is the bench.

| parameter | in | type | required | description |
|---|---|---|---|---|
| `device_id` | path | `string` | yes | The device's identity, as the listing reports it. |

- credential: bearer token. The client method is `getDeveloperDeviceCommands`
- request body: none
- response `200`: OK, `application/json` (`DevCommandsOutputBody`)
- errors: `401`, `403`, `404`, `422`, `500`, each a [problem document](../../error-codes.md)

#### Sample {#sample-get-developer-device-commands}

```sh
curl "http://127.0.0.1:8080/api/v1/dev/devices/9f2a4c18-6d3b-4e07-b5a1-8c0f2d7e4b93/commands" \
  -H "Authorization: Bearer $TOKEN"
```

```ts
await client.getDeveloperDeviceCommands({
  path: { device_id: "9f2a4c18-6d3b-4e07-b5a1-8c0f2d7e4b93" },
});
```

The server answers `200`:

### `get-developer-view` {#get-developer-view}

`GET /dev`. The developer view.

A page for somebody debugging a printer at a bench: the connectors this build carries, the resource instances and their supervision state, the printers that have dialled in, one printer in detail, and the event stream as it arrives. It holds no data of its own and reads the same operations any other client reads, so it shows exactly what the caller's credentials already reach.

It takes develop_device on the driver resource kind, which an org administrator holds on day one. The surface says what this binary is made of and what it sent to a machine, so it is not conferred by an identity alone and it is not view_resource: reading that a connector is declared is part of seeing the configuration, and this is the bench.

- credential: bearer token. The client method is `getDeveloperView`
- request body: none
- response `200`: The developer view, as one self-contained HTML document. It reaches nothing outside this origin and its Content-Security-Policy names its own script and stylesheet by content hash, `text/html` (`string`)
- errors: `401`, `403`, `500`, each a [problem document](../../error-codes.md)

This operation has no sample: one self-contained HTML page. It is read in a browser rather than parsed.
