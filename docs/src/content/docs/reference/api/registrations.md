A registration is a printer waiting at the door. It has dialled a connector,
shown a code on its screen, and is waiting for somebody to say it may come
in.

The printer starts it, and nothing in configuration does. It introduces
itself over the connector's own wire and displays a code. The listing shows
that code beside what the machine said it is, so an operator matches the
row against the printer in front of them. Approving answers the printer's
next poll with the credential it dials with from then on. The printer then
connects, appears under [devices](./devices.md) and publishes
`com.prusa.connect.device.arrived`. Every operation takes `admit_device`
on the `driver` resource kind. A connector configured to admit on arrival
puts nothing here, because nothing waits.

## Which operation to call {#which-operation}

| you want to | call |
|---|---|
| see which printers are waiting, and the code each one shows | [`list-pending-registrations`](#list-pending-registrations) |
| let one in, and learn the device id it became | [`approve-registration`](#approve-registration) |
| turn one away, or take back a credential already issued | [`reject-registration`](#reject-registration) |

A page adding a printer does not have to ask this listing on a timer. The
three registration events on
[`stream-events`](./events.md) carry the same exchange:
`com.prusa.connect.device.registration.announced` when a code arrives,
`.approved` when somebody lets it in, and `.rejected` when somebody turns it
away. The origin is the connector instance, and the approved frame carries
the device id, so a page follows a machine from the code to its device page
without asking again.

Rejecting is not permanent. It forgets the code and every credential behind
it, so an approved printer stops being accepted, but the printer registers
again at its next boot with a new code. To keep a machine off this server
permanently, take the network port away from it.

## Operations {#operations}

### `approve-registration` {#approve-registration}

`POST /api/v1/registrations/{code}/approve`. Let one device onto this server.

Approves the registration, so the device's next poll is answered with the credential it then dials with. The device appears on `/api/v1/devices` once it has dialled, which is its own next step and not this one: approving decides admission and does not open a connection.

Approving twice is the same answer as approving once. A code no connector holds is a 404, and so is one that was already rejected. It takes admit_device on the driver resource kind.

| parameter | in | type | required | description |
|---|---|---|---|---|
| `code` | path | `string` | yes | The registration code, as the listing reports it and as the device displays it. |

- credential: bearer token. The client method is `approveRegistration`
- request body: none
- response `200`: OK, `application/json` (`Registration`)
- errors: `401`, `403`, `404`, `422`, `500`, each a [problem document](../../error-codes.md)

#### Sample {#sample-approve-registration}

```sh
curl -X POST "http://127.0.0.1:8080/api/v1/registrations/K7PQ2XR4MN/approve" \
  -H "Authorization: Bearer $TOKEN"
```

```ts
await client.approveRegistration({
  path: { code: "K7PQ2XR4MN" },
});
```

The server answers `200`:

### `get-printer-authority` {#get-printer-authority}

`GET /api/v1/printer-authority`. The certificate of this server's own authority.

The DER file a printer loads from its USB drive as connect.der, so it trusts the certificate this server shows. It answers 404 when printers are not set up to trust this server's own authority, or when the wizard has not made one. It takes admit_device on the driver resource kind.

- credential: bearer token. The client method is `getPrinterAuthority`
- request body: none
- response `200`: The certificate, DER encoded, `application/pkix-cert` (`binary`)
- errors: `401`, `403`, `404`, `500`, each a [problem document](../../error-codes.md)

### `list-pending-registrations` {#list-pending-registrations}

`GET /api/v1/registrations`. The devices waiting to be let onto this server.

Every device that has introduced itself over a connector's own wire and is waiting for somebody to decide. Each row carries the code the device is displaying and what the machine said it is, so an operator can match a row against the machine in front of them before approving it.

A connector configured to approve on arrival puts nothing here, because nothing waits. So does a deployment whose connectors hold no registration table at all: the answer is an empty list rather than a refusal.

No row carries a credential. The token a connector issues is what the machine presents on its own wire, and this listing is not a second way to obtain one. It takes admit_device on the driver resource kind.

- credential: bearer token. The client method is `listPendingRegistrations`
- request body: none
- response `200`: OK, `application/json` (`ListRegistrationsOutputBody`)
- errors: `401`, `403`, `500`, each a [problem document](../../error-codes.md)

#### Sample {#sample-list-pending-registrations}

```sh
curl "http://127.0.0.1:8080/api/v1/registrations" \
  -H "Authorization: Bearer $TOKEN"
```

```ts
await client.listPendingRegistrations();
```

The server answers `200`:

### `reject-registration` {#reject-registration}

`DELETE /api/v1/registrations/{code}`. Turn one device away.

Forgets the registration and every credential it held, so a device that was already approved stops being accepted on the connector's wire.

It is not a permanent refusal. The device registers again at its next boot and is given a new code, so rejecting a machine somebody plugged in by mistake costs that machine one handshake. To keep a device off this server for good, take the port away from it.

A code no connector holds is a 404, and so is one that was already rejected. It takes admit_device on the driver resource kind.

| parameter | in | type | required | description |
|---|---|---|---|---|
| `code` | path | `string` | yes | The registration code, as the listing reports it and as the device displays it. |

- credential: bearer token. The client method is `rejectRegistration`
- request body: none
- response `204`: No Content, no body
- errors: `401`, `403`, `404`, `422`, `500`, each a [problem document](../../error-codes.md)

This operation has no sample: 204, for the same reason the resource delete is.
