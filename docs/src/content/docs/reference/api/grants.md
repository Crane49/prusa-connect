A grant is one line in the permission graph: this subject holds this
relation on this object. A `viewer` grant on `org:local` for `user:alice`
says Alice may see everything the org holds. Every other operation consults
the graph before it acts.

An object is an org, a device or a resource kind. A subject is a person, a
service account, a group's members, or a module's own instance such as
`sink:counter`. A relation is a role like `viewer` or `operator`, and the
[authorization vocabulary](../../authorization-vocabulary.md) says which
actions each one confers. Two rules decide every write: the caller
administers the object, and the grant confers nothing the caller does not
already hold there. So an administrator cannot hand out more than they
have. A grant written or withdrawn moves the permissions epoch, and every
open event stream is re-scoped to match.

A few verbs are dangerous: raw gcode, and anything marked irreversible. No
role confers one. A device's owner reaches them all and hands them out one
subject, one device and one verb at a time.

## Which operation to call {#which-operation}

| you want to | call |
|---|---|
| give a person or a module access to a fleet, a printer or a kind | [`write-grant`](#write-grant), [`withdraw-grant`](#withdraw-grant) |
| see who holds what on one object | [`list-grants`](#list-grants) |
| see what one person can do, printer by printer | [`list-subject-grants`](#list-subject-grants) |
| see the grants written for one person, printer by printer, a block included | [`list-subject-direct-grants`](#list-subject-direct-grants) |
| let one person run one dangerous verb on one printer | [`write-device-verb-grant`](#write-device-verb-grant), [`list-device-verb-grants`](#list-device-verb-grants), [`withdraw-device-verb-grant`](#withdraw-device-verb-grant) |
| accept a rebuild that lowered a verb's class | [`list-declaration-acceptances`](#list-declaration-acceptances), [`accept-declaration-change`](#accept-declaration-change) |

You may withdraw the grant you administer with, and nothing gives it back.
The first grant is written once, at bootstrap.

## Operations {#operations}

### `accept-declaration-change` {#accept-declaration-change}

`POST /api/v1/grants/kinds/{kind}/acceptances`. Accept a change to a declared kind that the host is holding.

This deployment records the class and the markings every declared verb was first seen with. A rebuild that raises a class or adds a marking applies on its own, because reach only narrows. One that lowers a class or removes a marking does not: the verb keeps what the record holds, the disagreement is named in the authorization vocabulary, and it applies from the next start once a row here accepts it by name. That turns the one genuinely silent supply-chain move, a rebuild pulling a version that quietly moves a verb down a class under grants written against the old one, into a visible difference that does nothing until a person moves it. Leaving verb out accepts a module rename instead: the kind's whole first-seen record moves onto the new module path, carrying every class and marking unchanged, so what moves is the publisher's name and never a pin.

| parameter | in | type | required | description |
|---|---|---|---|---|
| `kind` | path | `string` | yes | The device kind, qualified as the inventory renders it. |

- credential: bearer token. The client method is `acceptDeclarationChange`
- request body: `application/json` (`AcceptanceBody`), required
- response `201`: Created, `application/json` (`AcceptanceOutputBody`)
- errors: `400`, `401`, `403`, `422`, `500`, each a [problem document](../../error-codes.md)

#### Sample {#sample-accept-declaration-change}

```sh
curl -X POST "http://127.0.0.1:8080/api/v1/grants/kinds/acme.io%2Ffilament-shelf/acceptances" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "from": "configure",
    "module": "github.com/acme/prusa-adapter-shelf",
    "to": "operate",
    "verb": "acme.io.filament-shelf.command.calibrate_scale"
  }'
```

### `write-grant` {#write-grant}

`POST /api/v1/grants/{object_type}/{object_id}`. Write a grant.

Adds one tuple to the authorization graph. It answers 201 when the graph did not already hold it, which is also when the permissions epoch moved and every live event subscription re-scoped, and 200 when it did. Two rules decide it: the caller administers the object, and the grant confers nothing the caller does not already hold there. The second is what stops a caller granting themselves more than they have. On an org both rules read wider. Administering an org is holding the admin role on it, and an org tuple lands on every printer and every resource kind the org holds, so it is refused unless it confers nothing the caller lacks on each of them. One org tuple is how a fleet-wide grant is written, and org:&lt;org>#viewer@sink:&lt;name> is the whole of what feeds an event sink a fleet, including a printer admitted afterwards. The admin role itself cannot be conferred here: an org's first administrator is written at bootstrap.

| parameter | in | type | required | description |
|---|---|---|---|---|
| `object_type` | path | `one of org, device, resource_kind` | yes | The type of the object the grants are written on. |
| `object_id` | path | `string` | yes | The object's identifier, a DNS-1123 label. |

- credential: bearer token. The client method is `writeGrant`
- request body: `application/json` (`GrantBody`), required
- response `200`: The graph already held this grant. Nothing changed and the epoch did not move, `application/json` (`Grant`)
- response `201`: Created, `application/json` (`Grant`)
- errors: `400`, `401`, `403`, `422`, `500`, each a [problem document](../../error-codes.md)
