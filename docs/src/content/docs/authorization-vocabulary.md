The authorization graph is one of the four things this project does not make pluggable. Its whole vocabulary is below: what a caller can perform, what those things are performed on, the edges that join them, and every shape a stored edge is allowed to take.

A grant is a tuple, written `object#relation@subject`. A handler checks an **action**, never a role, so the role layer stays changeable without touching call sites, and the table of who confers what is the join between the two.

An action outside this set is refused rather than resolved: Go cannot stop a caller writing `Action("delete_everything")`, so the check does, and the refusal carries a code rather than a lookup that happens to miss.

## Vocabulary version

This build carries `authorization` version `4.2.0`, in format `1.0`. The content version moves when an action, a type, a relation or a permitted shape changes; the format version moves when the shape of an entry changes, so a consumer can tell a reshaped artefact from a reworded one.

## Actions

Every action belongs to exactly one object type. Asking for a printer action on a resource object is a refusal, not a lookup that misses, and the two masks share no bit.

`conferred by` names the relations that hand the action out **when they are written on an object of that type**. A role held further up reaches the object through a structure edge instead: `org` and `group` confer whatever the object they name holds.

### `observe` {#action-observe}

Read a device's live and recorded state.

- **on** `device`
- **conferred by** `parent`, `org`, `group`, `agent`, `viewer`, `operator`, `manager`, `owner`

Covers the telemetry stream, the current job, the file listing and every read of a device's condition. It is the floor of the device role layer: nothing below it reads anything, and every higher role contains it. No verb may carry it, because answering a verb writes to a transport that carries one command at a time.

### `operate` {#action-operate}

Send a verb of this class to a device: act on the machine in its normal duty.

- **on** `device`
- **conferred by** `parent`, `org`, `group`, `operator`, `manager`, `owner`

Pause, resume, home, set a target, stop a job, put a file on the machine, and every other verb the device's kind declares at this class. It is the floor a verb may carry: there is no read class for a verb. The kind's declaration decides which verbs exist; this action decides whether the caller may send one of them at all.

### `configure` {#action-configure}

Send a verb of this class to a device: change what the machine is, not the work on it.

- **on** `device`
- **conferred by** `parent`, `org`, `group`, `manager`, `owner`

Firmware, the token a printer reports under, the name it answers to on the network. It enters above operator because this server can undo none of them. A verb of this class is very often marked irreversible as well, which takes it out of every level and into a grant that names the verb.

### `administer` {#action-administer}

Administer the grants written on a device.

- **on** `device`
- **conferred by** `parent`, `org`, `group`, `manager`

The top of the device role layer, and the one action no verb may ever carry: a driver that could declare a verb of this class would be writing itself into the lattice. It is what a caller must hold in full before they can write another grant.

### `view_audit` {#action-view-audit}

Read who authorized which command on a device.

- **on** `device`
- **conferred by** `parent`, `org`, `group`, `manager`

The audit-class events a durable command record carries. It is conferred at manager and by nothing lower: an operator is a device viewer, and conferring audit sight at operator would let every device viewer learn which operator sent which command.

### `report_telemetry` {#action-report-telemetry}

Submit telemetry as the device itself.

- **on** `device`
- **conferred by** `agent`

Reachable only from the agent relation, which a device credential holds on its own device. It is deliberately outside every role mask, so a fleet-wide operator grant is not permission to forge a device's readings.

### `fetch_job` {#action-fetch-job}

Collect queued work as the device itself.

- **on** `device`
- **conferred by** `agent`

The other half of the device credential, reachable only from the agent relation. Together with report_telemetry it is what keeps a device credential from becoming an operator credential.

### `view_resource` {#action-view-resource}

Read the configuration of one resource kind.

- **on** `resource_kind`
- **conferred by** `org`, `viewer`, `operator`, `manager`

Covers listing instances of the kind and reading each one's declaration and status. Settings an implementation marks secret are redacted before this action sees them.

### `operate_resource` {#action-operate-resource}

Act on a running instance without rewriting its settings.

- **on** `resource_kind`
- **conferred by** `org`, `operator`, `manager`

Restart a failed sink, drain a queue, retry a connection. It is the resource-side equivalent of operate. The instance changes state and its declaration does not.

### `configure_resource` {#action-configure-resource}

Rewrite the settings block of a resource kind.

- **on** `resource_kind`
- **conferred by** `org`, `manager`

Create, edit and delete instances of the kind, including the settings a connection string lives in. It is the top of the resource role layer and is disjoint from every device action: a fleet-wide device grant is not permission to rewrite this server's storage configuration.

### `read_storage` {#action-read-storage}

Read what is inside an instance of the kind.

- **on** `resource_kind`
- **conferred by** `org`, `viewer`, `operator`, `manager`

Browse the entries of a storage instance and download a file's bytes. It is about contents and never about the declaration: view_resource says the instance exists and what it is configured as, and this says what is in it. Seeing that a storage backend is there and reading the files somebody put in it are not the same permission.

### `write_storage` {#action-write-storage}

Change what is inside an instance of the kind.

- **on** `resource_kind`
- **conferred by** `org`, `operator`, `manager`

Upload a file, create a folder, rename and delete. It is the write half of the contents surface and stops there: it is not configure_resource, so a caller who may drop a file into a storage instance may not repoint that instance at another directory, delete the instance, or administer the grants written on the kind.

### `admit_device` {#action-admit-device}

Decide which devices are let onto this server.

- **on** `resource_kind`
- **conferred by** `org`, `manager`

List the devices waiting at a connector's registration table, approve one so its next poll is answered with the credential it dials with, and turn one away. It is performed on the driver resource kind, because a registration table belongs to a connector. It is deliberately not configure_resource: rewriting a connector's settings is changing what this server dials, and admitting a machine is deciding who joins the fleet, so a site can hand a technician the second without the first.

### `develop_device` {#action-develop-device}

Reach the developer surface of this server.

- **on** `resource_kind`
- **conferred by** `org`, `manager`

Open the page at /dev, read which printer dialects this build carries and which paths this origin answers that the API document does not publish, and read the log of commands this process sent to one device. It is performed on the driver resource kind, because a connector is an instance of that kind and the command log is what went through one. It is deliberately not view_resource: reading that a connector is declared is part of seeing the configuration, and the developer surface says what this binary is made of and what it sent to a machine.

## Types

A **subject side** type may stand on the subject side of a tuple, whether as a principal holding a grant or as the object a structure edge points at. An **object side** type may have grants written on it. Some are both.

### `user` {#type-user}

One person, as an identity provider resolved them.

- **subject side** yes
- **object side** no

A user holds grants directly and through the groups they are a member of. The id is whatever the configured identity provider produced, so two providers naming the same person produce two subjects.

### `group` {#type-group}

A named set of people whose grants its members inherit.

- **subject side** yes
- **object side** yes

A group is written on the subject side of a grant as a userset, so granting a group operator on a device group is one tuple however many people are in it. Service accounts are deliberately not members: a robot never inherits a team's access.

### `service_account` {#type-service-account}

A non-human caller: a script, an integration or a job runner.

- **subject side** yes
- **object side** no

A service account holds grants written on it directly and never through a group or an org role, so a fleet-wide widening cannot reach one by accident. Every grant it holds was written for it on purpose.

### `device_credential` {#type-device-credential}

A device's own credential, and not the device.

- **subject side** yes
- **object side** no

A device credential is the subject of the agent relation on exactly one device, and of nothing else. It is the only type that reaches report_telemetry and fetch_job, and it reaches them on one device. The device it speaks for is the device type, which is the object a grant is written on.

### `node` {#type-node}

A federated peer site acting on this one's devices.

- **subject side** yes
- **object side** no

A node is written on the subject side of a device or device-group grant like a principal, so what a peer may do here is the same graph question as what a person may do, and it is answered locally rather than trusted from the wire.

### `sink` {#type-sink}

One configured event sink, as a holder of grants.

- **subject side** yes
- **object side** no

A sink is the instance an operator declared under sink:, reading the event bus as itself rather than as a service account of the same name. Nothing issues a credential for one and no caller can present it: it exists only while this server is supervising that instance. It is the one non-human type an org role accepts, and only at viewer, so org:local#viewer@sink:audit is the single tuple that feeds a sink the whole fleet including a printer admitted tomorrow.

### `history` {#type-history}

One configured history provider, as a holder of grants.

- **subject side** yes
- **object side** no

A history provider is the instance an operator declared under history:, reading the event bus as itself and storing what it is granted. Nothing issues a credential for one and no caller can present it. Like a sink it is accepted at org viewer and no higher, and that single tuple is what feeds it a printer admitted tomorrow: a provider holding hand-written per-origin grants stores nothing for the origins they miss, and a store with a hole in it is discovered when somebody needs the rows.

### `org` {#type-org}

The tenant everything else hangs under.

- **subject side** yes
- **object side** yes

An org carries the RBAC half of the model: admin, operator and viewer on the org reach every device in it at manager, operator and viewer level. It is the object side only, so nothing is ever granted to an org.

### `device_group` {#type-device-group}

A tree of devices that grants are inherited down.

- **subject side** yes
- **object side** yes

A device group stands on both sides: grants are written on it, and a device names its group so a grant there reaches every device under it. parent nests one group inside another, and the depth the resolver walks is bounded.

### `device` {#type-device}

One physical device.

- **subject side** yes
- **object side** yes

The object every device action is defined on. A device names its org and its group, so a grant written at either level reaches it without a tuple per device. Its kind says what type of device it is: this build registers printers and cameras. A device may also name another device as its parent, which is how a camera is reached by whoever may reach the printer it watches.

### `resource_kind` {#type-resource-kind}

The configuration surface of one resource kind.

- **subject side** no
- **object side** yes

Its ids are exactly the configurable resource kinds. A grant here governs every instance of that kind, because a resource instance is a line of this server's configuration and not a device somebody is given access to.

## Relations

A **role** relation carries a level and confers actions. A structure relation carries whatever the object it names holds, which is how one grant reaches a fleet.

### `member` {#relation-member}

Membership of a group.

- **role** no

The subject of a member edge inherits every grant written on the group as a userset.

### `parent` {#relation-parent}

One object nested inside another of its own type.

- **role** no

Grants on the parent reach everything beneath it. It nests one device group inside another, and it binds one device to another, which is a camera and the printer it watches. The walk is bounded, so a cycle a write created cannot become an unbounded resolve.

### `org` {#relation-org}

The tenant an object belongs to.

- **role** no

Structure, not a role. It is what makes an org admin reach a device without a tuple per device.

### `group` {#relation-group}

The device group a device sits in.

- **role** no

Structure, not a role. Moving a device between groups is one edge and changes every grant that reaches it.

### `agent` {#relation-agent}

A device's own credential, on that device.

- **role** no

The only relation that confers outside the role hierarchy, and the only one whose conferral a caller holding manager does not already hold. Writing one is refused unless the writer holds it too, which is what stops a session minting a device credential.

### `blocked` {#relation-blocked}

A deny that covers every action on the object.

- **role** no

It confers nothing and removes the role layer rather than adding to it, so it wins over any grant reaching the same subject from anywhere.

### `viewer` {#relation-viewer}

The read-only role.

- **role** yes

Confers observe on a device. Confers view_resource and read_storage on a resource kind. Every higher role contains it.

### `operator` {#relation-operator}

The day-to-day role.

- **role** yes

Contains viewer and adds operate on a device. Adds operate_resource and write_storage on a resource kind. These actions change what a device or an instance is doing, and what is inside one, without changing what it is.

### `manager` {#relation-manager}

The administering role.

- **role** yes

Contains operator and adds configure, administer and view_audit on a device. Adds configure_resource, admit_device and develop_device on a resource kind. A caller must hold this whole set before they may write a grant on the same object.

### `admin` {#relation-admin}

The org-wide manager role.

- **role** yes

Exists only on org, and reaches every device in the org at manager level. It is the RBAC half of the model.

### `owner` {#relation-owner}

Whose machine this is.

- **role** no

Not a role, and it carries no level. It adds observe, operate and configure to whatever the role layer already gives its subject. It also reaches every dangerous verb of the owned device's kind. So somebody who owns a device and holds only operator on it may flash it, and an operator who owns nothing may not. It stops short of administer, so an owner cannot hand ownership on. Whoever administers the device writes this edge. It stops short of view_audit too. It is written on the device, so it is inherited from nothing and a block on the same device removes it.

## Permitted shapes

## Reading the set from a running server

`GET /api/v1/vocabularies/authorization` answers with what **this build** carries, from the same accessors this page is generated from. It is public: the vocabulary names no principal, no grant and no instance, and an operator reading a refusal needs to know which action was checked and which relation would confer it.
