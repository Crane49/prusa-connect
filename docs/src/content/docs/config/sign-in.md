The first run decides whether people sign in at all. The setup wizard asks
it right after the setup code and the choice of path, and creates the first
administrator when they do.

People sign in in one of two ways:

- **A password stored on this server.** The wizard turns it on when you choose
  who may use the server, and `core.auth.local` does it in your file.
  `password_memory_bytes` and `password_passes` set how much work checking one
  password takes: more is safer against guessing and slower on a small
  computer. `password_hashes_at_once` sets how many checks run at the same
  time. See
  [Local accounts](../local-accounts.md).
- **A sign-in provider you already run,** such as Keycloak or Authentik,
  over OpenID Connect. `core.auth.issuer`, `client_id` and `redirect_uri` name
  it, and `client_secret` when the provider issued one: Google and a new
  Keycloak or Authentik client need it, a public client has none. The wizard
  offers it on both paths. It asks for the administrator's subject at the
  provider, the `sub` claim, and writes it as `core.principal`, so whoever
  signs in with that subject administers the server. Any subject works. The
  wizard reads the issuer's discovery document before it restarts and refuses one it
  cannot read. See
  [Signing in at an OpenID Connect provider](../human-auth.md#signing-in-at-an-openid-connect-provider).

The two cannot be on together. Once a provider is set, the server holds no
local accounts, and a username and password login is refused.

If you add a provider to `config.yaml` yourself, without the wizard, set
`core.principal` to the administrator's subject too. Left at the default
`operator`, nobody who signs in administers the server, and the server logs a
warning at start-up. To find your subject, sign in once and read the
`subject` of the line `a person signed in at the identity provider` in the
server log. Then set it as `core.principal` and restart.

`core.principal` is the user every request runs as when nobody signs in, and
the id the first administrator is created under. It is not the name the
administrator signs in with. `core.auth.setup_code` fixes the one-time setup
code for an install a script sets up.

The session cookie is marked Secure when `core.api.tls` is set, so a browser
sends it only over HTTPS.
